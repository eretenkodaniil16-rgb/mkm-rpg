# Player Modifiers

## Status

This document is the design baseline for MKM player-side RPG modifiers. It intentionally defines the *modifier vocabulary* before the final primary attribute set and formulas are chosen.

Primary attributes and player modifiers are different concepts:

- **Primary attributes** are persistent character-build inputs chosen later (the current STR/DEX/VIT set remains a prototype).
- **Player modifiers** are gameplay-facing values consumed by combat, movement, resource, spell and progression systems.
- Equipment, skills, buffs, debuffs and temporary effects may contribute to the same modifier snapshot later without being persisted as final values in `CharacterData`.

The final player modifier snapshot should conceptually be derived as:

`base values + primary attributes + level progression + equipment + skills + buffs/debuffs + temporary effects = player modifier snapshot`

Exact formulas, units, caps and primary-attribute mappings are deliberately unresolved at this stage.

| ID | Name | Purpose |
| --- | --- | --- |

| `spell_damage` | Spell damage | General multiplier for damaging spells. |
| `magic_penetration` | Magic penetration | Reduces effective magical resistance of the target. |
| `spell_critical_damage` | Spell critical damage | Bonus applied when a spell qualifies for a critical outcome. |
| `cast_speed` | Cast speed | Modifies cast time for spells that have a casting phase. |
| `spell_range` | Spell range | Modifies range of spells whose design permits scalable range. |
| `spell_area` | Spell area | Modifies area/radius of compatible area spells. |
| `spell_projectile_speed` | Spell projectile speed | Modifies projectile velocity for compatible projectile spells. |
| `spell_duration` | Spell duration | Modifies duration of compatible persistent magical effects. |
| `spell_status_power` | Spell status power | Modifies magical status buildup/application strength for compatible spells. |
| `healing_power` | Healing power | Scales healing generated by the player's spells and magical abilities. |
| `barrier_power` | Barrier power | Scales shields/barriers generated by compatible magical abilities. |

## Magical defense

| ID | Name | Purpose |
| --- | --- | --- |
| `magic_resistance` | Magic resistance | General mitigation against magical damage. |
| `elemental_resistance` | Elemental resistance | Extension point for school/element-specific resistance once the final magic schools are defined. |

Element-specific keys such as fire, frost, lightning, arcane, holy or shadow are intentionally **not** fixed yet. The world/lore and spell-school design should define the final set first.

## Explicit exclusions from the core player modifier set

- **Initiative:** not part of MKM combat. Combat remains real-time rather than turn-based.
- **Accuracy and evasion rolls:** a physically valid Minecraft hit should not be converted into a hidden RPG miss roll.
- **Player-wide attack reach:** reach should primarily belong to weapon/spell design, because a character statistic should not make every weapon reach unnaturally far.
- **Mandatory random critical chance:** critical outcomes should primarily reward gameplay conditions (vanilla criticals, weak points, backstabs, stagger windows, abilities). A small random-critical mechanic can be reconsidered later if it adds value.
- **Final elemental/magic schools:** deferred until the magic system and setting establish them.

## Calculation and cap policy

Modifiers should have explicit units and safety bounds when they become authoritative. Percentage resistances, movement multipliers, attack speed, cooldown recovery, penetration and similar values must not be allowed to stack without limits.

A future modifier definition should therefore carry at least:

- stable ID;
- base/default value;
- unit/operation semantics;
- minimum and maximum allowed values;
- aggregation rules;
- whether the value is authoritative server-side, presentation-only, or both.

Final modifier values should be calculated rather than persisted whenever possible. Persistent character data should store durable build choices and sources, not a stale copy of every derived combat number.

## Next design step

Define the final primary attribute set and map each primary attribute to one or more modifiers in this document. Only after that mapping is reviewed should the prototype STR/DEX/VIT schema be treated as replaceable or migrated.
