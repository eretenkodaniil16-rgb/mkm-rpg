# MKM RPG — Character M4: расы, классы, происхождение, схема сохранения и QA

**Статус:** начальный работающий прототип, draft [PR #55](https://github.com/eretenkodaniil16-rgb/mkm-rpg/pull/55). **Основа:** интегрированный Fabric PR #45 (включает CharacterData v4 / World E2.1 / Equipment D3). Minecraft 26.3, Java 25, Fabric Loader 0.20.1. Ни PR #35, ни PR #45, ни исторический NeoForge `main` не объединяются этим PR.

## 1. Исследовательское решение: три модели развития

Оценка 1–5: **5 означает наиболее благоприятный** вариант для текущей архитектуры MKM, не объективную универсальную оценку жанров.

| Критерий | Жёсткие классы | Бесклассовая | Гибрид |
| --- | --- | --- | --- |
| Понятность стартовой роли | 5 | 2 | 4 |
| Разнообразие между прохождениями | 4 | 2–4 (зависит от билдов) | 5 |
| Управляемость баланса PvE/PvP | 4 | 2 | 4 |
| Свобода развития игрока | 2 | 5 | 4 |
| Сопровождаемость системы до lvl100 | 3 | 2 | 4 |
| Простота первой реализации | 3 | 4 без эксклюзивных способностей | 4 |
| Совместимость с существующим v4 миром | 3 | 5 | 5 при отдельном профиле |

**Выбор: гибрид**, но не немедленное дерево талантов. Фиксированный стартовый класс даёт понятную роль/визуальный образ, специализации (в будущем) — выраженные направления, а ограниченные внеклассовые приёмы — пространство для нестандартных билдов. Текущие семь характеристик `STR/DEX/VIT/END/INT/WIL/PER`, уровни 1–100 и начисление 2 очков/уровень остаются без изменений. Нельзя внезапно закрывать текущий ванильный меч, щит, добычу блоков или уже работающий `mkm:renewal` для воина: это было бы регрессией на пользовательском сохранении.

**Предлагаемая шкала на перспективу:** уровни 1–20 — базовые способности класса; 20/40/60/80 — *кандидаты* на развилки развития, 100 — capstone. Это **только проектирование**, никакой выдачи очков специализации, respec, мультикласса или нового дерева на сервере пока нет. После 100 уровней требования к XP/очкам не меняются.

### Две модели расы

- **Преимущественно косметическое происхождение:** проще баланс, нет преимущества в PvP и конвертации мира, но слабая разница в игре и меньшая реиграбельность. Рекомендуется как fallback/accessibility для мультиплеера.
- **Полноценная физиология:** явные особенности питания, солнца, дыхания, размеров и хитбокса, устойчивостей и ресурсов. Даёт разнообразие, **но в Minecraft меняет collision, PvP reach, проходы, броню, сон, еду, анимации и баланс модов**; это отдельная система, сейчас слишком рискованная.
- **Для M4 выбран компромисс:** разные маленькие бонусы к уже определённым `PlayerModifierId`, идентификаторы особенностей и косметическая идентичность, **без изменения физических размеров, ванильной физиологии или хитбоксов**. Расовые численные различия предварительны.

## 2. Реализованный каталог — четыре комбинации

| ID расы | Пробная особенность / ключи `PlayerModifierSnapshot` |
| --- | --- |
| `mkm:human` | `mkm:adaptable`: `STAMINA_REGENERATION +0.20`, `MANA_REGENERATION +0.10` |
| `mkm:dwarf` | `mkm:stoneborn`: `MAX_HEALTH +2`, `BLOCK_STABILITY +0.08` |

| ID класса | Особенность / ключи `PlayerModifierSnapshot` | Рекомендация стартовой способности |
| --- | --- | --- |
| `mkm:warrior` | `mkm:martial_training`: `MELEE_DAMAGE +0.035`, `STAMINA_COST −0.025` | Нет автоматически выдаваемого навыка |
| `mkm:mage` | `mkm:arcane_studies`: `MAX_MANA +6`, `HEALING_POWER +0.035` | `mkm:renewal` (существующее публичное заклинание) |

Комбинации Человек/Воин, Человек/Маг, Дворф/Воин, Дворф/Маг проверяются одними и теми же серверными правилами выбора. **Не обещается**, что warrior обладает уникальной активной атакой или mage эксклюзивно владеет Renewal: Combat/Ability Core ещё не принял контракт выдачи новых исполнимых способностей. Бонусы считаются **складываемыми дельтами до единственного финального clamp** из `PlayerModifierCalculator`. `EquipmentSnapshots.snapshot` остаётся общей точкой для Combat, Renewal и листа персонажа; никакого нового применения урона/мана-событий.

### Какие ID в данных неизменны

`RaceDefinition`: `id`, `titleKey`, `traitIds`, `modifierDeltas`. `ClassDefinition`: `id`, `titleKey`, `traitIds`, `startingAbilityIds`, `specializationIds`, `modifierDeltas`. Все ID — стабильные `mkm:<path>` из белого списка каталога, сервер не принимает произвольный JSON скрипт или имя класса Java. Локализация не меняет сохранённые идентификаторы.

`OriginCatalog` — временный Java-каталог (явный allowlist); доступ к данным не требует отражения (reflection), загрузки классов, исполняемых скриптов, eval или обхода диска.

### Контракты владения

- **Character:** идентичность, XP, семь статов, неизменяемые награды, в будущем валидируемые durable unlock IDs и prereq, но пока без выдачи нового права на применение способности.
- **Equipment:** текущие ванильные `ItemStack` и слоты; бонусы из снаряжения суммируются с Race/Class **один раз**. Нет предметных запретов.
- **Combat:** решает фактические попадания, расход выносливости, тайминг, отмену атаки, защиту, последствия. Никогда не вычислять урон по экрану/позе.
- **Ability:** server-only проверка исполнимого обработчика, ресурса, разрешения, таргетинга. `startingAbilityIds` являются пока metadata, не grant на сервер. Не создавать второй кастер заклинаний.
- **MNAE:** только косметические анимации; в `CharacterData` и `CharacterOriginData` нет кадров, поз, костей и проигрывателя.

## 3. Точная миграция v4 / новая схема сохранений

**Ключевое решение:** `CharacterData` остаётся **schema v4, без изменения структуры, размера и прежнего codec.** Для новой возможности введён *отдельный* Fabric player attachment `mkm:character_origin` **schema v1**. Таким образом не нужен опасный v4→v5 rewrite единого персонажа ради опциональной расы/класса.

Сохраняемая структура `mkm:character_origin`:

```json
{
  "schema_version": 1,
  "revision": 1,
  "race_id": "mkm:dwarf",
  "class_id": "mkm:mage"
}
```

Отсутствующий attachment у уже существующего игрока (v1/v2/v3/v4, в том числе пользовательский `0.0.5-fabric.4`) означает **UNSELECTED**, а не «нового персонажа»: дефолт `{"schema_version":1,"revision":0,"race_id":"","class_id":""}`. Инициализация нового attachment при входе **не меняет** `mkm:character`, `earned_points`, `allocated_points`, `claimed_reward_ids` или состояние World E2.1. В момент одного успешного выбора сервер **один раз** сохраняет пару и переводит revision 0→1. Редактирование/повторный выбор отклоняется; отдельный respec пока отсутствует.

Поля, оставленные без изменения в `mkm:character`: `schema_version=4`, `experience` (long), `strength`, `dexterity`, `vitality`, `endurance`, `intelligence`, `willpower`, `perception` (int), `earned_points` (int), `allocated_points` (7 int STR/DEX/VIT/END/INT/WIL/PER), `claimed_reward_ids` (список строк, серверный приватный). `CharacterAttachments.CHARACTER` не переименован; `copyOnDeath()` сохраняется. Новый `CharacterOriginAttachments.PROFILE` также имеет `persistent(CODEC)`, `copyOnDeath()`, `targetOnly()` sync.

В обеих записях **никаких косметических и анимационных состояний**. Если неизвестен ID каталога из будущего мода, запись не стирается; бонусы не начисляются до разрешения совместимости. При schema origin будущей версии сервер блокирует изменение. Старые персонажи могут **добровольно** выбрать класс даже при высоком уровне без перерасчёта их опыта или очков; UI не открывается насильно на входе.

Независимые Character/Origin attachments находятся в логическом playerdata. Однако `copyOnDeath` подтверждён исходным Fabric registration и unit-тесты проверяют сериализацию; **реальная death/relog/падение питания отдельно требуют тестирования на сервере.**

## 4. Сетевой протокол и UI

В Character Sheet на K появилась кнопка «Раса и класс». Открывается `CharacterOriginScreen` с двумя расами, двумя классами и предварительным описанием. Подтверждение отправляет `OriginSelectionRequest(requestId,expectedRevision,raceId,classId)` **без** XP, численных бонусов, предметов, UUID, прав, заклинаний или новых статов. Сервер проверяет alive/non-spectator, `CharacterData v4`, известные ID, revision и one-shot lock. Ответ `OriginSelectionResult` — только коррелированная подсказка; авторитетное состояние приходит через синхронизацию attachment владельцу. Предположенная «кнопка назад» возвращает лист персонажа без изменения.

**Ограничение:** при минимальном прототипе нет автоматического полноэкранного «обязательного первого входа»: это намеренно сохраняет существующие миры. Первый выбор доступен через K. На следующих стадиях при утверждении onboarding можно отображать неперекрывающий подсказочный тост для новых профилей, но не менять серверную политику.

## 5. Расширяемый каталог на перспективу (проект, не реализация)

Кандидаты 6 рас: человек, дворф, эльф, орк, гном, полурослик. На будущее допускается отдельное поле `heritage_variant` с миграцией **только после** баланса и визуальных требований; текущая строка race ID не меняется.

Кандидаты 8 классов и пар специализаций (пока только **список**, кроме двух M4 определений):
1. Воин → Страж / Дуэлянт.
2. Маг → Арканист / Маг защиты.
3. Следопыт → Охотник / Разведчик.
4. Плут → Ассасин / Трикстер.
5. Жрец → Целитель / Инквизитор.
6. Паладин → Защитник / Каратель.
7. Друид → Хранитель природы / Оборотень (особенно высокое влияние на MNAE).
8. Ремесленник → Изобретатель / Алхимик.

Потенциальные вне-классовые приёмы — ограниченные через верифицированный сервером бюджет специализации, но **никаких правил, стоимости, точек мультикласса, ограничений оружия и уровневых порогов сейчас не изменяем**.

## 6. Data-driven перспектива для Fabric 26.3

Fabric 26.3 поддерживает [reloadable custom dynamic registries](https://fabricmc.net/2026/09/15/263.html) и Mojang `Codec` для типизированных JSON. Следующая версия может переместить Race/Class Definitions из Java-констант в серверный datapack, но каталог M4 пока нарочно статический. До внедрения необходимо:

1. Отдельные registries `mkm:race` и `mkm:class`, стабильные `ResourceKey` и синхронизация строго ограниченного описательного поднабора клиенту. Сервер — единственная инстанция, вычисляющая игровые характеристики; отсутствие клиента с datapack не означает «исполнять недоверенное содержимое».
2. Codec с `schema_version`, allowlist `PlayerModifierId`, `traitId`, заранее зарегистрированных `effect_type`, bounded finite числа, лимиты длины и размера коллекции; проверка дубликатов и ссылок между классами; запрет циклов и несуществующих ID. Не принимать inline Java, имена классов, текстовые скрипты, eval, выражения, произвольные команды, пути файлов, пакеты или кастомные `DamageSource`.
3. Для `combat_skill` и `spell` хранить **только ссылки на заранее зарегистрированные обработчики**; отсутствие обработчика = ability остаётся disabled, даже если запись каталога валидна.
4. Влияние datapack reload на уже сохранённые профили — отдельная миграционная политика. Не удалять сохранённые ID, не менять ранее выбранную расу молча. До явной миграции неизвестный ID = нулевой bonus + операторская диагностика.

Официальная справка: [Fabric 26.3 update](https://fabricmc.net/2026/09/15/263.html) и [Fabric Codecs](https://docs.fabricmc.net/develop/serialization/codecs). API регистрации проверять по установленной `fabric_api_version=0.165.0+26.3` перед внедрением, не копировать вслепую сигнатуры из 26.2.

**Release policy:** Branch/PR остаются draft, публикация финального JAR для пользовательского сохранения требует прежде всего ORIG-02, 03, 04, 06 и 09.
